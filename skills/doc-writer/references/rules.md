# 写作规则

动笔前完整读取。禁用句式、排除性检验和中文排版见 `references/constraints-writing.md`。

## 1. 结构

- **结论先行**：全文开头给结论或用途，每节首句概括本节要点，再展开细节。只读每节首句应能复述全文。
- **逐层回答**：每一节回答上一层引出的问题；同级要点互不重叠，合起来覆盖上一层。回答不了任何问题的节删掉。
- **标题用标准名**：用户指定的骨架照用；否则模板章节名就是标题，自定义节用名词短语说明内容（"缓存策略"），不写成结论句或状态（"缓存不可行""结果缺失"）。
- **决策类文档**（技术设计、ADR、PRD）：读者在开头就能找到决定——有概述节就写在概述里；模板规定先写背景的（如 Nygard ADR）按模板顺序。元数据压成一行放在结论之后或文末。

## 2. 内容

- **具体**：判断绑定可观测的事实——谁、做了什么、数字多少、边界在哪。
- **判断有理由**：职责要求决策时给明确立场、理由和取舍：选了什么，牺牲了什么。多个目标给优先级和排序依据。参考文档陈述契约，ADR 记录已有决议，不替读者做决定。
- **可操作**：概念和原则要能说明具体做什么、不做什么；排除不了任何方案的原则删掉。分析维度从当前问题推导，不机械套"技术／业务／组织"。
- **范围**：开头说明覆盖什么、不覆盖什么；范围外的内容即使正确也删。描述项目本身的文档写当前设计，不写成本轮修改记录。
- **一物一名**：术语首次出现时用一句话定义，此后名称和含义不变；一个词只指一个对象，多义词加限定语（"schema 版本""期望版本"）。代码标识照原样写，不意译。

## 3. 真实

只写已知事实。具体化和真实冲突时，真实优先：宁可写"未知"，不为显得具体而编造。

- 实测数据写来源和时间，估算写依据，假设写成立条件和失效后果。
- 关键论述让读者分得清哪些是事实、哪些是假设、哪些是判断，不必给每句加标签。
- 影响读者决策的未知（如"阈值要大于最长处理时间，但没有实测数据"）在"未决问题"集中列一次，写明怎样确认、谁来定；其他节不重复提，不加"不保证""仅供参考""未经验证"之类的免责话。模板表格里的状态值（"待定""待定位"）照模板写。
- 写作过程不进正文：跑了哪些示例、没跑测试、没渲染图、怎样核对的，写在交付说明里给委托人看。
- 目标值和契约值（"单次最多 1000 条"）说明是要求或约定即可。

## 4. 密度

- 每句提供新信息；删除后不影响理解的句子删掉，包括铺垫、重复总结、结尾升华。
- 长度反映权重：重要的多写，不重要的少写，没有的不写。不为对称补条目，不为覆盖模板写空节。
- 必需节缺材料时，能问就在第 1 步问；问不到就省略该节，缺口写进交付说明，不在正文写"未提供，请向维护者确认"。该节是读者要的主体时（如没有日志的测试报告的结果）保留节名，写一句缺什么数据、从哪里补，不填数值。
- 必要的限制在原处写一次，不反复声明。
- 编辑已有文档时保留作者的经验、立场和有效表达，事实修正说明依据。
