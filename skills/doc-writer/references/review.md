# 范围、比例与呈现
写作 agent 动笔前读，审核 agent 审查时读。
文档里写重的风险、写早的决定，会变成评审门槛和施工负担，所以写的时候就按这里把握分量。

## 重点审核项
审核时先从文档里挑出这几类内容，逐项核对证据，因为它们一旦写错或写重，代价最大：
需求与非需求、验收标准、设计决定与主要代价、风险与阻塞项、对外契约（接口、数据、状态）。

## 该不该现在决定
对每条风险、边界、非目标、代价、未决问题和建议，先问这一句。

- 现在决定：不可逆，或改起来昂贵，或影响结构、接口、依赖、跨团队契约，或不定下来实现者会遇到周期内解决不了的未知。这类决定要写清选了什么和理由。
- 留给施工：其余都是。删掉，必要时只留一句约束，如「实现时按 X 决定」。实现者有更多信息，留给他们判断更准。
- 为推测的未来需求预留能力，以及锁、CAS、压测后再定这类加固建议，删除。预建的能力要付构建、延迟和维护复杂度三份成本。
- 介绍现有系统的文档只写现状，不写给上游或维护者的改进建议，也不写「是否应该」类问题。研究中发现的上游代码缺陷写进交付说明，不进文档的未决问题。
- 尚未定下的重要决定可标为「提议中」，不要写成已定。

## 写多重
- 能改变本次决策的，保留并写透。
- 后果可控的，降为一行「已知限制」，写明触发条件和影响。
- 纯推测的，删除。只有「可能」「万一」、说不出概率或影响的风险，多半属于这一类。
- 阻塞项只在以下情形成立：不可逆；不解决就无法估计工作量；触及安全或数据丢失底线。
- 非目标只写被有意排除的合理目标，并给理由。目标的反面（如「系统不应崩溃」）和凑数的条目都删。
- 非目标、代价、风险、未决问题、跨领域关注点都是可选节，内容会改变本次决定时才写。

## 图和表
- 一张图只回答一个问题。图前用一句话引出它回答什么，图后写解读，补充图里没有的条件和限制。
- 状态图只画对象会停留等待事件的状态，顶层不超过约 7 个，多了就拆成嵌套状态。只做分流的中间步骤写在转移条件里。
- 多方交互的核心机制画时序图，参与者不超过 5 个。只画主路径和 1–2 个关键失败或竞争分支，失败分支用 `alt` 画到「返回什么」为止。
- 参数、字段、枚举、多分支的结果用表格，不画图。纯线性步骤和只有两个组件的关系用编号列表。
- 图里的名称与正文、代码、术语表一致。颜色和形状不单独表达含义，需要时配文字说明。
- 图文要平衡：表格不超过一节篇幅的一半，表格前后也要有解释它的段落。

## 篇幅与形式
- 重要机制写透：讲清怎么工作、为什么这样、失败时怎样，建议每个子节至少两段。不设字数下限，也不为覆盖章节写空节。
- 段落一般 3–6 句，一段一个主题，中心句放段首。单句一般不超过 60 字。
- 每节首句给出本节结论，只读首句也能复述全文。
- 标题用标准章节名或名词短语，不写成结论句。
- 引用：正文只在关键结论处给 `文件:行号`，其余集中到文末「依据」节，密集的行内引用会打断阅读。
- 总结只写决定、代价和适用条件，不复述正文。
