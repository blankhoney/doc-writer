# 解决、比例与呈现
解决阶段的分诊 subagent 判断 `edges.md` 的条目时读，写作 agent 动笔前读，需求与范围核查 agent 审查时读。
讨论在写作之前完成，文档只记录结论。交付审核时才出现的风险和疑问会变成评审门槛和施工负担，所以按这里在上游处理掉。

## 重点审核项
审核时先挑出这几类内容，逐项核对证据，因为它们一旦写错，代价最大：
需求、验收标准、设计决定与主要代价、对外契约（接口、数据、状态）、阻塞项。

## 该不该现在决定
对 `edges.md` 的每一条先问这一句。

- 现在决定：不可逆，或改起来昂贵，或影响结构、接口、依赖、跨团队契约，或不定下来实现者会遇到周期内解决不了的未知。写清选了什么和理由。
- 留给施工：其余都是。删除，因为实现者有更多信息，判断更准。
- 为推测的未来需求预留能力，以及锁、CAS、压测后再定这类加固建议，删除。预建的能力要付构建、延迟和维护复杂度三份成本。
- 与「前提」矛盾的条目，删除。部署规模、已接受的取舍和用户已定的决定已经回答了它。
- 现状文档只写现状。上游代码缺陷写进交付说明，不写进文档。

## 写多重
- 能改变本次决策的，写成结论并写透。
- 后果可控、纯推测的，删除。只有「可能」「万一」、说不出概率或影响的风险，多半属于这一类。
- 阻塞项只在以下情形成立：不可逆；不解决就无法估计工作量；触及安全或数据丢失底线。成立的才记进待问清单，记之前先查已有文档、ADR、代码注释、提交信息和 issue 讨论，已有取舍的写成一句决定。
- 风险、已知限制、非目标、跨领域关注点，默认不写，用户要求时才写。未解决的问题不进文档，也不设「待决定」「未决问题」节，用户明确要求时除外。问题只出现在交付后的那一轮提问里，用户确认要写的再补进文档。
- 已知限制只在读者不知道就会用错时写，每条写明触发条件和影响。
- 非目标只写被有意排除的合理目标，并给理由。目标的反面和凑数的条目都删。
- 尚未定下的重要决定标为「提议中」，不写成已定。

## 图和表
- 一张图只回答一个问题。图前用一句话引出它回答什么，图后写解读，补充图里没有的条件和限制。
- 状态图只画对象会停留等待事件的状态，顶层不超过约 7 个，多了就拆成嵌套状态。只做分流的中间步骤写在转移条件里。
- 多方交互的核心机制画时序图，参与者不超过 5 个。只画主路径和 1–2 个关键失败或竞争分支，失败分支用 `alt` 画到「返回什么」为止。
- 参数、字段、枚举、多分支的结果用表格，不画图。纯线性步骤和只有两个组件的关系用编号列表。
- 图里的名称与正文、代码、术语表一致。颜色和形状不单独表达含义，需要时配文字说明。

## 篇幅与形式
- 重要机制写透：讲清怎么工作、为什么这样、失败时怎样。不设字数下限，也不为覆盖章节写空节。
- 一段一个主题，中心句放段首。段落和句子的长度线见 `references/formatting.md`。
- 每节首句给出本节结论，只读首句也能复述全文。
- 标题用标准章节名或名词短语，不写成结论句。
- 引用：正文只在关键结论处给 `文件:行号`，其余集中到文末「依据」节，密集的行内引用会打断阅读。
- 总结只写决定、代价和适用条件，不复述正文。
