# 编排
主 agent 开工前读本文件。各阶段的产出都写进工作目录，主 agent 只记路径和一行摘要。
这样主上下文始终很短，到最后一步仍能看清整体。

派子 agent 的方式：用当前环境的派发工具，或用命令行调用其他模型（如 `pi -p` 调 DeepSeek）。
研究、核对、对齐用便宜模型即可，推理强度调高；写作和审核用当前可用的较强模型。
子 agent 也可以再派子 agent，层数按任务大小定。环境不能派子 agent 时，主 agent 按同样的阶段自己做，每阶段结束只保留文件。

## 工作目录
工作目录放在临时目录或用户指定的位置，交付后按用户意愿保留或删除。

| 文件 | 产出阶段 | 内容 |
|---|---|---|
| `definition.md` | 定义 | 文档做什么、读者、要回答的问题、范围、篇数 |
| `notes/<主题>.md` | 研究 | 每个子 agent 一份笔记，每条附 `文件:行号` 或 URL |
| `brief.md`、`glossary.md` | 梳理 | 章节大纲与每节要回答的问题；术语表 |
| `product-outline.md` 或 `architecture.md` | 梳理 | 产品梳理，或架构与数据模型 |
| 文档正文 | 写作 | 交付给用户的文档 |
| `review-table.md` | 审查 | 不超过 20 行的处理表 |
| `align-report.md` | 对齐 | 对齐发现和处理结果 |

## 1. 定义
主 agent 自己写 `definition.md`，五到十行：
- 文档做什么：读者读完要做出什么决定或动作。
- 读者：按使用者、运维、开发者、评审者分层，写明主要读者是哪一层。
- 要回答的问题：列出读者最想问的三到八个问题，后面每个阶段都以它为准。
- 范围：覆盖什么、不覆盖什么、依据哪个版本的代码。
- 片段类型：文档含哪几类片段，各对应哪份写作指南。
- 用户视角：面向使用者时，写明需要的端到端示例和界面呈现（截图、命令行输出、报表）。

一个请求默认写一篇。只有用户要求，或两类读者的任务在一篇里完成不了时才拆分。
拆成多篇时，每条契约、状态定义和术语只归一篇文档定义，其他文档链接过去，因为复述的副本会在下次修改时过时。
多篇按 PRD、设计、API 与 Runbook 的顺序写，下游以上游为准。
影响内容的歧义集中问用户一轮，每问附默认答案。信息足够就直接往下做。

## 2. 研究
按 `definition.md` 拆出 4–6 个研究主题，并发派出，每个子 agent 一个主题。
笔记条数不设上限，因为写作 agent 只能依据笔记里有的事实。
技术类常见主题：数据模型、状态与转换、主要流程与失败路径、错误与重试、并发与一致性、已有文档和测试声称的行为。
产品类先研究用户是谁、在什么场景用、为什么需要、现在怎么做、痛点在哪，再研究现有能力与限制。
```text
任务：回答以下问题：<问题列表>。范围：<目录或 URL>。只读，不改项目文件。
产出：写入 <工作目录>/notes/<主题>.md，每条一行事实，附 文件:行号 或 URL，推断单独标出。完成后回复一行摘要。
```

## 3. 梳理
派一个新子 agent，只给它 `definition.md` 和 `notes/` 的路径，产出 `brief.md`、`glossary.md` 和梳理文件。
产品类的 `product-outline.md` 写用户、场景、需求清单与优先级、关键流程；技术类的 `architecture.md` 写组成与职责、数据模型、状态与流程、关键取舍。

术语表每条一行，列为：术语、定义、代码标识、不要混用的近义词。
- 同一个词只指一个对象。「版本」「状态」「任务」这类词指两种以上对象时，各起限定名，如「schema 版本」「期望版本」。
- 状态名在正文、表格、图里写法一致，首次出现写中文名和代码值。
- 登记、领取、接纳这类业务动作，各写清触发者、前置状态和结果状态，同一动作不换近义词。
- 术语表放进文档的「术语」节。多篇文档时只放一处，其他文档链接过去。
```text
任务：读 <工作目录>/definition.md 和 notes/，写 brief.md、glossary.md 和 <梳理文件>。
brief.md 给出章节大纲，每节一句要回答的问题，并注明依据哪些笔记。完成后回复一行摘要。
```

## 4. 写作
派一个新上下文的写作 agent，它只读梳理文件和下方提示里列出的指南。
新上下文能避免研究阶段的大量原文挤占写作注意力。缺事实时，写作 agent 回查代码，或派小子 agent 补研。
长文按章节派多个 lead，每个 lead 写一组章节，最后由一个 agent 合稿、去重、理顺过渡。
```text
任务：按 <工作目录>/brief.md 写 <文档路径> 的 <章节范围>。缺事实时回查代码或派子 agent 补研。
先读：<写作指南路径>、references/review.md、references/constraints-writing.md、references/unslop.md、glossary.md、<梳理文件>。完成后回复一行摘要。
```

## 5. 审查
派一个审核 agent，只给它文档、`definition.md` 和代码路径，不给研究笔记和写作过程。
它没有写作时的沉没成本，才能看出哪些内容写重了、哪些决定不该现在做。
```text
任务：审查 <文档路径>。先读 references/review.md 和 <工作目录>/definition.md，代码在 <代码路径>。
挑出重点审核项，每项可派便宜的子 agent 核对证据，然后直接修改文档。
处理表写入 <工作目录>/review-table.md，列为：条目、判断、处理（保留／降为已知限制／删除／改写）。
```

## 6. 对齐
派一个新子 agent 核对文档与代码、文档与文档之间的一致性。
修改文档集中的任何一篇后都要做这一步，即使只改了一个词，因为改名最容易留下旧名。
```text
任务：核对 <文档路径列表> 与 <代码路径>。变更清单：<改名、契约变化、删掉的概念>。
查：旧名残留、与术语表不符的叫法、过时的函数名和字段名、多篇之间矛盾的契约、权威文档之外的重复定义。
按 references/unslop.md 逐条扫一遍，再运行 doc-lint 并逐条判断候选。确定的问题直接修正，其余写进 <工作目录>/align-report.md。
```

主 agent 读 `review-table.md` 和 `align-report.md`，抽查两三处改动，然后交付。
交付说明三五行：写了什么、依据哪些代码、删减了什么、还有哪些没核对。
