# 编排
完整档读本文件，轻量档不读。把每阶段的产出写成文件，交接只传路径和一行摘要，因为原文会挤占判断的上下文。

## 分工
| 角色 | 数量 | 做什么 | 不做什么 |
|---|---|---|---|
| 主 session | 1 | 定义文档，派研究、写作和核查，维护笔记索引，梳理，合稿和修改，交付 | 深读代码，写正文 |
| subagent | 按需 | 只做一件事，结果写进文件 | 再决定文档结构 |

主 session 兼任每篇文档的 lead，多篇时按顺序逐篇做。环境允许子 agent 再派子 agent、且文档多于一篇时，可以每篇派一个 lead，由 lead 承担本文件中「主 session」在研究、梳理、写作和修改中的职责，主 session 只定义、派核查、汇总待问问题和交付。

1. 主 session 为定义范围可读 README、目录结构、入口文件和提交记录；缺事实时派补研 subagent，不自己沿调用链读代码，因为代码会挤占判断用的上下文。
2. 长文可按章节派写作 subagent，由主 session 合稿。
3. 等派出的 agent 全部返回，再进入下一阶段或交付。后台运行的 agent 返回前不结束回合；等待时靠完成通知，不轮询。
4. 产出文件缺失或 subagent 被限流时，重派或改为串行，不跳过阶段。
5. 子 agent 提示只写任务、产出和参考文件的绝对路径；规则让它自己读，因为工作目录可能不同。

子 agent 读不到文件系统时，由主 session 写作和核查，子 agent 只收集分析并交回文本。

用便宜模型派研究，调高推理强度；写作和核查可用较强模型。
环境允许时，可用命令行调其他模型。不能派子 agent 时，按同样阶段自己做，每阶段结束只保留文件。按三张证据表依次自查，交付时注明没有独立核查。

## 工作目录
放在临时目录或用户指定的位置，交付后按用户意愿处理。

| 文件 | 用途 |
|---|---|
| `definition.md` | 文档定义 |
| `notes/index.md`、`notes/<主题>.md` | 文档集共用的研究笔记，格式见 `references/notes.md` |
| `questions.md` | 待问用户的问题 |
| `brief.md`、`glossary.md` | 大纲和术语表 |
| `evidence/<核查名>.md` | 核查证据表 |

## 研究笔记
- 按 `references/notes.md` 写。
- 同一篇笔记同一时间只由一个 agent 改，因为同时修改会互相覆盖。下游引用上游已有笔记，不重新研究同一主题。

## 五阶段
### 1. 定义（主 session）
写 `definition.md`，列出以下内容：

| 项目 | 内容 |
|---|---|
| 用户原话 | 用户对本文档的要求，只摘与本文档相关的，逐条原样保存，核查时据此对照 |
| 目的 | 读者读完要做出的决定或动作 |
| 读者 | 使用者、运维、开发者、评审者，标明主要读者 |
| 问题 | 三到八个，编号为 Q1…Qn，后续阶段都以此为准 |
| 范围 | 覆盖与排除的内容、代码版本 |
| 片段类型 | 对应的写作指南 |
| 用户视角 | 端到端示例和界面呈现 |
| 前提 | 部署规模、并发假设、已接受的取舍、用户已定决定 |

默认写一篇；用户要求或两类读者的任务一篇完成不了时，再拆分。

拆成多篇时，每条契约、状态定义和术语只归一篇定义，其他文档链接过去。
按 PRD、设计、API、Runbook 的顺序写多篇，下游以上游为准。

目的、读者、范围有歧义时，动笔前问一轮，每问附默认答案，因为答错要整篇重写。
从轻量档升级时，把已有笔记按主题对到 Q 编号写进索引，研究阶段只研究缺的 Q。

前提不清楚时，按代码和常规用法定假设，在定义里标「？」。查实后去掉「？」；写作者不把带「？」的假设当事实写进正文。按假设删掉条目且符合待问标准时，把假设记进 `questions.md`，因为假设错了就要补回内容。

### 2. 研究（主 session 派探索 subagent）
并发派 4–6 个，每个研究一个主题。

| 文档 | 研究主题 |
|---|---|
| 技术类 | 数据模型、状态与转换、主要流程与失败路径、错误与重试、文档和测试声称的行为。定义的问题要求时，再研究并发与一致性 |
| 产品类 | 先研究用户、场景、痛点和现状，再看现有能力 |

```text
任务：回答 <Q 编号和问题>。范围：<目录或 URL>。只读。先读 <工作目录>/definition.md 的范围、版本和前提。
产出：<工作目录>/notes/<主题>.md，先读 <技能包根目录>/SKILL.md 的「读哪个文件」表，读表中写笔记的 agent 要读的文件，按它写。回交一行索引。
```
主 session 把索引行追加进 `notes/index.md`。

### 3. 梳理（主 session）
读 `definition.md`、`notes/index.md` 和 `references/review.md`，按 Q 编号读对应笔记，连同定义里标「？」的假设一起处理。同一对象在两篇笔记里说法不同的，在两篇的「疑问」节标「冲突」。按以下顺序处理各篇的「疑问」：
1. 代码、配置或已有文档能回答的，派补研查清，改写进笔记正文。
2. 与前提矛盾、真实使用中不会触发的，删除。
3. 施工期能决定的，删除。
4. 符合 `references/review.md` 待问标准的，先查已有文档、ADR、设计说明、代码注释、提交信息，以及能访问的 issue 和 PR 讨论。查到就按已定取舍改写成一句决定，查不到就记进 `questions.md`，每问附推荐答案，文档里不写，因为可能早已权衡过。用户说明是方案初版时，这类问题同时写进文末一节，见 `SKILL.md` 硬性要求 4。

`questions.md` 只放符合 `references/review.md` 待问标准的问题。skill 规则已定的事、已有依据删掉的内容，不问。
提问不阻塞写作。交付后由主 session 一次问用户，因为零散提问会打断写作。
- 用户确认要写时，先改写对应笔记，再补写文档。对受影响的章节和引用文档重跑核查。
- 用户答不需要处理时，丢弃；答已考虑过时，把用户给的取舍写进笔记和需要它的正文，不再追问。

写 `brief.md`，每节写一句要回答的问题和依据的笔记路径与节名。brief 引用的冲突和推断，派核实 subagent 查清并改写笔记，再派写作。

把产品梳理、架构与数据模型并入 brief，不另建文件。
附图表计划，按 `references/formatting.md` 逐节判断，列出图的类型、问题和配表。分章写作时按计划画，因为单个写作者看不到全文结构。
写 `glossary.md`，列术语、定义、代码标识和不要混用的近义词，规则见 `SKILL.md` 硬性要求 2。
- 把术语表放进文档的「术语」节，多篇只放一处。

### 4. 写作（写作 subagent）
派新上下文的写作 subagent。读 `definition.md`、brief、术语表、负责章节在 brief 里引用的笔记，`SKILL.md` 的硬性要求和「边界」，以及文件表中适用的写作参考。正文事实取自定义里已确认的前提与用户决定、笔记和其中的代码摘录。笔记缺细节时，只按笔记给的 `文件:行号` 打开那几行，不自己搜索代码。笔记「疑问」节的内容不写进正文。

篇幅按 `references/formatting.md` 的写透要求定，派写作时不给字数上限，图按 brief 的图表计划画，不限张数，因为上限会让写作者删掉该写的内容。
轻量档已写的正文作为初稿交给写作 subagent，按 brief 和笔记改写。缺事实时，在回交里列出；主 session 派补研写进笔记后，派写作 subagent 补写那几处。

### 5. 核查（主 session 并行派 3 个 agent，统一修改）
派不继承写作上下文的核查 agent，环境允许时可再派 subagent。改已有文档时，三项核查只查本次写的部分和与它相关的位置。只写 `evidence/<核查名>.md`，不改文档，因为并行修改会互相覆盖。

| 核查 | 做什么 | 证据表列 |
|---|---|---|
| 事实与一致 | 按 `SKILL.md`「边界」先定依据的时点，笔记首行的版本与定义不符的列出。把正文断言逐条对到笔记。数据写在哪里、对外契约、默认值、公式和数值，以及状态转换、调用关系和失败行为，对照笔记里的代码摘录核对，不只对照笔记结论，因为笔记结论的误读会被正文照抄；没有摘录的，按笔记给的 `文件:行号` 打开那几行核对；笔记没覆盖的断言，或依赖摘录之外的配置和调用方的，从断言涉及的代码沿调用链查，不做全仓搜索。设计决定、用户确认和运行结果对照定义、设计记录或运行输出核对。示例的每一步与图、表和正文对照，不一致的列出；全文搜索多篇及仓库已有文档的术语、契约、默认值；只列冲突和重复定义 | 断言、文档位置、依据、符合／不符／无依据、建议 |
| 需求与范围 | 先核需求、验收标准、设计决定与代价、对外契约，因为这几类写错代价最大。把用户原话和定义的每个问题对到章节，标出遗漏、多写和偏离。再做读者演练：按定义里的每类读者，只看文档完成他们的任务（实现、写用例、评审拍板、操作、调用），记下每处卡住、只能猜、要回头问人，或会读错、推出错误结论的地方，因为定义的问题覆盖不到读者实际要用的全部信息；同时标出未解决讨论。按「梳理」顺序回溯并按 `references/review.md` 判断；需问用户的标「待问」 | 条目、对应章节或读者任务、判断、建议（补写／改写／删除） |
| 文风与排版 | 执行下列四步 | 位置、问题、依据、建议 |

1. 用一句话复述主旨和章节结构；复述不出时，先报结构问题。
2. 按 `SKILL.md` 运行 doc-lint，逐条判断候选。
3. 按 `references/unslop.md`、`references/formatting.md` 和 `references/constraints-writing.md` 逐条核对。逐节查配图条件，满足却没有图的记进证据表。
4. 对摘要和各章首句的结论问：假设是什么、证据在哪、有无替代方案、后果是什么。

等三张表全部返回，由主 session 一次改完：
1. 按依据改正不符项，先改笔记再改正文；改一个数值或行为时，同步改正文、表、图和示例里的所有出现处。本次写的无依据内容删掉，影响正文的记进 `questions.md`；改已有文档时原有内容不删。
2. 把「待问」项记进 `questions.md`。
3. 跨文档冲突只改用户授权的文档，保留一个权威出处，其余链接过去；未授权的只在交付说明列出。
4. 两张表的建议冲突时，以事实为先，再顾排版。
5. 按 `SKILL.md` 重跑 doc-lint，把处理结果补进证据表。

主 session 读完三张表和处理结果，抽查两三处改动，再交付。

```text
任务：核查 <文档路径列表>，核查类型：<名称>。笔记索引：<工作目录>/notes/index.md。
依据：<definition.md、代码路径、术语表、用户材料>。先读 <参考文件>。
证据表写入 <工作目录>/evidence/<名称>.md，列为 <表头>。不改文档。
```

用三五行交付说明写清：写了什么、依据哪些代码、删减了什么、哪些没核对。
