# 编排
主 session 开工前读本文件。
每个阶段的产出都写成文件，上层只记路径和一行摘要，因为读代码和读资料的原文会挤占写作和判断的上下文。

## 三层分工
| 层 | 数量 | 做什么 | 不做什么 |
|---|---|---|---|
| 主 session | 1 | 定义文档集，指定术语表和共享契约的权威文档，派 lead，派核查，汇总，交付 | 读代码，写正文 |
| lead | 每篇文档 1 个 | 本文的 orchestrator：派探索 subagent，用总结写 brief 和术语表，派新上下文的写作 subagent，合稿 | 读代码 |
| subagent | 按需 | 只做一件事，结果写进文件 | 再决定文档结构 |

规则：
1. lead 缺事实时，派补研 subagent，不自己翻代码。
2. 长文可按章节派写作 subagent，由 lead 合稿，统一术语并去重。
3. 每个 subagent 回交一行摘要和文件路径，不回贴正文。
4. 派出的 agent 没有全部返回，不进入下一阶段，也不交付。
5. 产出文件缺失或 subagent 被限流，就重派或改为串行，不跳过这一阶段。
6. 子 agent 提示只写任务和产出。写作规则由它自己读对应的参考文件，提示里不重复。

子 agent 用便宜模型即可，推理强度调高。写作和核查可用较强模型。
环境允许时，也可以用命令行调其他模型（如 `pi -p`）。环境不能派子 agent 时，按同样的阶段自己做，每阶段结束只保留文件。

## 工作目录
放在临时目录或用户指定的位置，交付后按用户意愿处理。
- `definition.md`：文档做什么、读者、要回答的问题、范围、篇数。
- `notes/<主题>.md`：研究笔记，每条带 `文件:行号` 或 URL。
- `brief.md`、`glossary.md`、梳理文件：大纲、术语表、产品梳理或架构与数据模型。
- `evidence/<核查名>.md`：核查证据表。

## 阶段
### 1. 定义（主 session）
写 `definition.md`，五到十行：
- 文档做什么：读者读完要做出什么决定或动作。
- 读者：按使用者、运维、开发者、评审者分层，写明主要读者。
- 要回答的问题：三到八个，后面每个阶段都以它为准。
- 范围：覆盖什么、不覆盖什么、依据哪个版本的代码。
- 片段类型：各对应哪份写作指南。
- 用户视角：需要的端到端示例和界面呈现。

一个请求默认写一篇。只有用户要求，或两类读者在一篇里完成不了任务时才拆分。
拆成多篇时，每条契约、状态定义和术语只归一篇文档定义，其他文档链接过去。
多篇按 PRD、设计、API 与 Runbook 的顺序写，下游以上游为准。
影响内容的歧义集中问用户一轮，每问附默认答案。

### 2. 研究（lead 派探索 subagent）
并发派 4–6 个，每个一个主题：代码、数据与配置、已有文档、架构分析。
技术类常见主题有数据模型、状态与转换、主要流程与失败路径、错误与重试、并发与一致性、已有文档和测试声称的行为。
产品类先研究用户、场景、痛点和现状，再看现有能力。
```text
任务：回答 <问题列表>。范围：<目录或 URL>。只读。
产出：<工作目录>/notes/<主题>.md，每条一行事实，附 文件:行号，推断单独标出。回交一行摘要。
```

### 3. 梳理（lead）
读全部笔记，写 `brief.md`（每节一句要回答的问题和依据的笔记）、`glossary.md` 和梳理文件。
术语表列为：术语、定义、代码标识、不要混用的近义词。
- 同一个词只指一个对象。指两种以上时各起限定名，如「schema 版本」「期望版本」。
- 状态名在正文、表格、图里写法一致，首次出现写中文名和代码值。
- 业务动作各写清触发者、前置状态和结果状态，同一动作不换近义词。
- 术语表放进文档的「术语」节。多篇文档只放一处。

### 4. 写作（写作 subagent）
lead 派新上下文的写作 subagent，长文按章节派多个，由 lead 合稿。写作 subagent 只读 `brief.md`、术语表、梳理文件和以下参考：对应的 `references/writing/` 指南、`references/formatting.md`、`references/review.md`、`references/constraints-writing.md`、`references/unslop.md`。
缺事实时派补研 subagent。

### 5. 核查（主 session 并行派 5 个 agent）
核查 agent 不继承写作上下文，各自可再派 subagent。
每个 agent 必须把证据表写进 `evidence/<核查名>.md`，直接修正确定的问题，回交一行摘要。
主 session 读完全部五张证据表才交付，抽查两三处改动。

| 核查 | 做什么 | 证据表列 |
|---|---|---|
| 事实 | 抽出文档里每个可核查的断言：名称、字段、默认值、数值、状态、调用关系、行为。按章节分给 subagent，对照代码逐条核对。不符的修正，无法确认的删除或改写成待确认 | 断言、文档位置、证据 `文件:行号`、符合／不符／无法确认 |
| 需求对齐 | 用户原话和 `definition.md` 的每个问题，都要对应到文档章节。标出遗漏、多写和偏离 | 需求或问题、对应章节、遗漏／多写／偏离／符合、处理 |
| 跨文档一致 | 多篇文档，或文档与仓库已有文档之间，对每个术语、契约、默认值做全文搜索，列出所有出处。同一项只留一个权威出处，其余链接过去。即使只改了一个词也要做，因为改名最容易留下旧名 | 术语或契约、各出处、权威出处、处理 |
| 范围与比例 | 按 `references/review.md` 审，处理表写入 `evidence/scope.md` | 条目、判断、处理（保留／降为已知限制／删除／改写） |
| 文风与排版 | 见下 | 位置、问题、依据、处理 |

文风与排版核查按顺序做：
1. 用一句话复述全文主旨和章节结构。复述不出来就判结构不合格，先改结构，再看细节。
2. 运行 doc-lint，逐条判断候选，包括 G1 表和排版候选。
3. 按 `references/unslop.md` 逐条扫，按 `references/formatting.md` 逐条对照。步骤和规则类句子应是祈使句。
4. 对每个关键结论问四件事：假设是什么，证据在哪，有无替代方案，后果是什么。
5. 逐章过六项：清晰、准确、精确、相关、深度、逻辑。广度和公正由需求对齐与范围与比例核查负责。

```text
任务：核查 <文档路径列表>，核查类型：<名称>。依据：<definition.md、代码路径、术语表>。
先读 <参考文件>。证据表写入 <工作目录>/evidence/<名称>.md，列为 <表头>。回交一行摘要。
```

交付说明三五行：写了什么、依据哪些代码、删减了什么、还有哪些没核对。
