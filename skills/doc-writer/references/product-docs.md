# 产品类文档

PRD、Changelog（Release Note）和面向使用者的 README 读本文件。产品类文档回答"给谁解决什么问题、用户能做什么、怎样算做成"，读者是产品经理、业务方、研发评审和使用者。

## 1. 语言

用产品经理的规范语言：用户、场景、问题、需求、业务规则、验收标准、优先级、指标。

- 需求写用户能做什么、看到什么结果，不写怎么实现。函数签名、类型、SQL、表结构、索引属于技术设计；PRD 只在"技术约束"里点出影响产品决策的限制（如"重试次数从现有数据推算不准，需要新增计数"）。
- 用用户的词，不用代码的词：写"消息失败后自动重试"，不写"`retry()` 把 `status` 置为 `READY`"。需要对齐代码名时在术语表里对应一次。
- 每条需求可验证：有明确的触发条件、预期结果和边界。
- PRD 不写源码行号、代码示例和接口参数；取材得到的 `文件:行号` 用来核对，不抄进 PRD。现有能力用用户能观察到的行为描述。

## 2. PRD 要讲清的内容

| 内容 | 讲清什么 | 常见缺失 |
|---|---|---|
| 背景与问题 | 谁在什么场景遇到什么问题，现在怎么绕过，代价是什么 | 只写"需要支持 X"，不写为什么 |
| 目标与非目标 | 这次要达成的结果；明确不做的事及原因 | 非目标空着，评审时范围失控 |
| 用户与场景 | 主要用户、典型场景、使用频率；每个场景一句话描述用户目标 | 用户写成"开发者"一个词 |
| 需求 | 用户能做什么、看到什么；按场景或功能分组，每条有编号和优先级（P0 必须、P1 应该、P2 可以） | 没有优先级，全部同等重要 |
| 业务规则 | 状态、条件、边界值、异常时用户看到什么；规则冲突时以哪条为准 | 只写正常路径 |
| 验收标准 | 每条 P0/P1 需求至少一条可验证条件，回指需求编号；可用"给定／当／那么"写法 | 验收写成"功能正常" |
| 成功指标 | 上线后看什么数据判断成功：业务指标（采用率、问题减少量）和质量门槛（错误率、性能），写清口径和目标值；目标值写依据（现有基线、对标），没有依据时写"待定"并在未决问题里写由谁何时定 | 只有正确性门槛，没有业务指标；目标值凭空给出 |
| 里程碑 | 分阶段交付内容和时间；时间未定时写明由谁何时确定 | 完全缺失 |
| 风险与未决问题 | 影响范围或排期的不确定项，每项写选项、默认建议、决策人 | 未决问题没有负责人 |

读者测试：产品经理读完能否拍板做不做，研发读完能否估算工作量。

## 3. 用户视角的呈现

- 有界面的产品：用线框、真实截图或界面流程图展示关键步骤；拿不到真实界面时写"待补截图"，不编造。
- 命令行工具和库：用一段完整的使用示例展示用户视角——用户写什么、得到什么、出错时看到什么。示例写用户代码，不写库的内部实现。
- 多步骤的业务流程：用一个端到端场景串起来，从用户的起点写到最终结果。

## 4. Changelog 与面向使用者的 README

- Changelog 和 Release Note 写这个版本对使用者意味着什么：新能力、行为变化、升级要做什么。破坏性变更放最前面并给出升级步骤。
- 面向使用者的 README 首屏回答三件事：这是什么、适合谁、怎么开始；安装和最小可用示例必须能照着跑通。
