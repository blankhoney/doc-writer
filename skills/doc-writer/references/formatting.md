# 排版与结构
先选呈现方式，再写句子，因为排版决定能否扫读。用祈使句写规则和步骤。

## 呈现方式
| 内容 | 用 | 不用 |
|---|---|---|
| 有先后的动作 | 编号步骤，每步只写一个动作，条件放在指令前 | 段落里串联步骤 |
| 并列事项 | 按「硬线」选列表 | 句内罗列 |
| 多属性对照、枚举、多分支结果 | 表格，单元格不超过 2 句 | 每项一段重复结构 |
| 状态转换、多方交互、分支流程 | 按「图文比例」配图 | 文字复述图中内容 |
| 论证和因果 | 短段 | 把推理拆成列表 |

## 硬线
1. 纯文字段落不超过 200 字、5 句；超过就拆段或改呈现方式。
2. 单个分句不超过 40 字；超过就在连词处拆开。
3. 一句里串联的事项超过 2 个时，改成列表。
4. 标题不超过 3 级，不跳级；用标准章节名或名词短语，不写结论句。
5. 并列事项的列表每组不超过 5 项；超过就分组。编号步骤、字段、状态、错误码不受限。

## 字符
- 加粗只用于界面元素和列表项开头的行内标题，强调靠措辞，因为满篇加粗就没有重点。
- 函数、字段、参数、路径、文件名、命令、环境变量、状态码用行内代码，不加引号；占位符写成 `<名称>`。
- 多行内容和要读者执行的命令放进围栏代码块并标语言，因为读者要整段复制。
- 中文与英文之间加半角空格；中文与数字之间加不加，全文统一。
- 破折号只用于插入说明或解释，不用来串联句子。

## 结构
1. 按文档类型写开头摘要：PRD 概述一两句，技术设计 3–5 句，其他类型按内容需要定。写清现状、问题、本文回答什么和答案，让读者单读开头也知道结论。
2. 一段只写一个主题，每节首句写结论，再写支撑，因为读者会扫读首句。
3. 故障和错误按「现象、原因、处理」三列写，因为排查从现象查起。
4. 把结果写成可验证的现象，因为读者需要判断是否成功。

句内删减与篇幅：
1. 删开场白、复述和客套；真实的不确定保留一句。
2. 只在句内压缩：删虚词，保留因果、条件、否定和单位。保留完整句子，不改成箭头或自造缩写；表格单元格和图中短标签除外。
3. 写透重要机制，讲清工作方式、理由和失败行为。不设字数下限，也不为覆盖章节写空节。

## 图文比例
按内容判断配图，不按篇幅；满足下列条件就画，因为表格不能代替关系和走向。

| 条件 | 呈现 |
|---|---|
| 对象有 3 个以上状态且会转换 | 状态图 |
| 3 个以上组件有读写或调用关系 | 结构图 |
| 判断有 3 条以上分支 | 流程图 |
| 多于两个参与方按时间交互，或有失败、竞争分支 | 时序图 |
| 两个参与方的简单请求响应、纯线性步骤 | 编号列表 |

- 一张图只回答一个问题。每张图表前后各用一两句引出问题、解释条件和限制，不复述图中内容。
- 状态图只画等待事件的状态，顶层不超过约 7 个；多了就嵌套。把分流的中间步骤写进转移条件。
- 时序图的参与者不超过 5 个；画主路径和 1–2 个关键失败或竞争分支。用 `alt` 把失败分支画到返回结果。
- 图表并存并互相对照：图画关系和走向，表列含义、条件和代码位置，正文沿图讲解并指向表行。只有参数和字段清单可单独用表。
- 图中名称按 `references/orchestration.md` 的术语表规则统一。颜色和形状不单独表达含义，配文字说明。
