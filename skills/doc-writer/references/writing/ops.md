# 运维文档（Runbook、部署手册、操作步骤、复盘）
用 SRE 和运维的语言写可以立即执行的步骤，让值班人员在压力下照着做也不出错。
读者是值班人员和操作者，他们多半是在出事时才打开文档。

## 标准章节
Runbook 每条对应一个告警或症状：

| 章节 | 要回答的问题 |
|---|---|
| 触发症状 | 看到哪个告警、哪种现象时用这一条？ |
| 影响 | 用户和下游会受到什么影响，紧急程度多高？ |
| 诊断步骤 | 按什么顺序查，每步看什么、正常和异常各是什么样？ |
| 处置 | 每种诊断结果对应做什么，做完应看到什么？ |
| 回滚 | 处置失败或恶化时怎样恢复到操作前？ |
| 升级路径 | 什么情况下找谁，带哪些信息？ |

部署手册和操作步骤：前置条件、步骤、验证、回滚；回滚在操作不可逆时必写，其余可选。

复盘：概要、影响（给具体数字）、时间线（注明时区）、促成因素、处置经过、做得好与不好（可选）、行动项。

## 语言要点
- 每步用祈使句开头，一步一个动作。值班人员一次只能盯一件事。
- 条件写在指令前面，例如「如果队列积压超过 1 万，扩容消费者」。条件放后面，读者可能先执行了再看到条件。
- 关键步骤后写「应看到……」，给出命令输出或指标的正常样子，读者才能判断这一步成功了没有。
- 命令写成可直接复制的代码块，占位符用尖括号标出，并说明从哪里取值。
- 原理只写一两句，需要时链接设计文档。出事时没人读长文。
- 复盘按系统和流程叙述，不点名追责。改得了系统和流程，改不了人。
- 每个行动项写负责人。没有负责人的行动项不会被执行。

## 这一类的反模式
- 告警对应的 Runbook 缺失，或告警本身无法立即行动。
- 步骤依赖某个人的经验，例如「找老王确认」，没有写出要确认什么。
- 文档随生产环境变化而过期，命令和指标名已经对不上。
