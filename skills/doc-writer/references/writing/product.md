# 产品需求（PRD、需求评审稿）
用产品经理的规范语言，从用户和业务视角讲清要解决什么问题、做到什么程度算成功。
读者是业务方、研发和测试，他们读完要能决定做不做、估出工作量、写出测试。

## 标准章节
| 章节 | 要回答的问题 |
|---|---|
| 概述 | 做什么、给谁做、为什么现在做？一两句，单独读也能讲清价值 |
| 背景与问题 | 谁在什么场景遇到什么问题，现在怎么绕过，代价多大？ |
| 目标与成功指标 | 做成是什么样，上线后看哪个数据，口径和目标值是什么？ |
| 用户与场景 | 主要用户是谁，典型场景有哪些，各自想完成什么？ |
| 范围与非目标（非目标可选） | 这次做哪些；哪些合理目标被有意排除，为什么？ |
| 需求 | 用户能做什么、看到什么？按 MoSCoW 标优先级 |
| 关键流程 | 用户从起点到最终结果的端到端体验是什么，界面上看到什么？ |
| 业务规则 | 状态、条件、边界值和异常时用户看到什么，规则冲突时以哪条为准？ |
| 验收标准 | 每条 Must 和 Should 需求怎样判定做完？ |
| 术语 | 本文的业务名词各指什么？ |
| 假设（可选） | 对用户行为和业务做了哪些假设，哪条不成立会改变方案？ |
| 里程碑（可选） | 分几期交付，每期交付什么？ |
| 未决问题（可选） | 哪些需要业务方拍板的问题会改变范围或排期？ |

## 语言要点
- 需求写结果，不写做法。函数名、字段名、表结构、接口参数和示例代码都不放进来，它们属于技术设计，写进来会限制研发选择实现。
- 自检每条需求：换一种实现，这句措辞要不要改？要改就重写。
- 一条需求只讲一件事，只有一种理解，能被验证或度量。需求按功能分组，用小标题或数字编号，验收标准用需求名回指。
- 优先级用 Must、Should、Could、Won't 四档。全部标成 Must 等于没有排序。
- 验收标准用 Given/When/Then，写行为不写点击步骤，正向和反向场景都写。界面一改，绑定点击步骤的标准就要跟着改。
- 成功指标的目标值要有依据，例如现有基线或业务约定。没有数据时如实写明尚无基线、由谁何时补，不编造基线和目标值。
- 关键流程用一个端到端场景串起来，写用户的操作和看到的结果。有界面时放线框或真实截图，没有就写「待补截图」。
- 用户故事写出具体角色和要做的决定。写不出具体角色时改用场景描述，因为套用格式本身不产生信息。

## 这一类的反模式
- 功能罗列，说不出每个功能解决哪个痛点。
- 目标用户写成「所有用户」或「开发者」一个词。
- 一次写死所有细节，不给研发和设计留判断空间。
