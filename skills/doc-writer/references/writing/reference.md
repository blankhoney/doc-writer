# API 与参考文档
用参考文档的语言中性地陈述契约，让调用方查到一项就能正确使用它。
读者是调用方开发者，他们按名字查找，很少从头读。

## 标准章节
| 章节 | 要回答的问题 |
|---|---|
| 概述 | 这组接口做什么，入口在哪，最常用的是哪几个？ |
| 鉴权与约定（可选） | 怎么认证，通用的请求头、分页、时间格式、错误格式是什么？ |
| 每个接口：签名 | 方法、路径或函数签名是什么？ |
| 每个接口：参数 | 每个参数的类型、是否必填、取值范围、默认值和各取值的行为是什么？ |
| 每个接口：返回值 | 成功时返回什么字段，各字段的含义和类型是什么？ |
| 每个接口：错误 | 会返回哪些错误，各自的触发条件是什么，调用方能否重试？ |
| 每个接口：示例 | 一个最小的真实请求和响应长什么样？ |
| 限制与配额（可选） | 有哪些频率、大小、并发限制，超出时发生什么？ |
| 版本与兼容（可选） | 哪些变更会破坏调用方，弃用的接口何时移除？ |

## 语言要点
- 结构照产品结构排，一个模块一节，一个接口一小节，读者才能按名字定位。
- 每个接口用同样的小节和同样的字段顺序。一致的格式让读者一眼找到要的那一列。
- 首句说明接口做什么，用现在时，不重复接口名。
- 布尔参数分别写 true 和 false 的行为，再写默认值。只写「是否启用」时，读者猜不出关闭后的行为。
- 限制写成条件句，例如「设置 a 时必须同时设置 b」，条件放在指令前面。
- 参数、字段、错误码用表格。示例用真实运行得到的请求和响应，没运行过的不写输出。
- 代码标识不当动词用，例如写「发送 `POST` 请求」，不写「`POST` 数据」。

## 这一类的反模式
- 在参考里讲设计争论、背景故事或教程步骤。这些内容改为链接到设计文档或操作指南。
- 同一字段在不同接口里叫法、类型或单位不一致。
- 只列成功响应，不列错误。
