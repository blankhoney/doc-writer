# 技术设计、ADR 与原理说明
用技术设计的规范语言讲清机制、约束和取舍，让评审者能判断方案是否成立，让实现者能据此动手。
读者是研发和架构评审者。

## 标准章节
| 章节 | 要回答的问题 |
|---|---|
| 概述 | 结论是什么：选了什么方案，为什么选它？ |
| 背景与范围 | 现状是什么，要解决的问题和约束是什么？只写事实，不重写需求 |
| 目标与非目标（非目标可选） | 方案要达成什么；哪些本可成为目标的事有意不做？ |
| 设计 / 组成与职责 | 有哪些组件，各管什么，依赖方向和进程、存储边界在哪？ |
| 设计 / 数据模型 | 有哪些实体和字段，约束、默认值和字段间不变量是什么？ |
| 设计 / 状态与流程 | 对象有哪些状态，谁触发转换，主流程和关键失败路径怎么走？ |
| 设计 / 错误处理 | 各类错误调用方看到什么，能否重试，重试是否幂等？ |
| 设计 / 并发与一致性（可选） | 事务和锁的边界在哪，竞争时结果是什么？ |
| 设计 / 示例 | 一个最小的端到端例子，输入什么、经过哪些步骤、得到什么？ |
| 备选方案（可选） | 有真实被否决的方案时：它是什么，为什么不选？ |
| 兼容与迁移（可选） | 旧数据和旧调用方怎么处理，怎么回滚？ |
| 跨领域关注点（可选） | 安全、隐私、可观测性上有哪些本设计特有的边界？ |
| 未决问题（可选） | 哪些必须由需求方或维护者先拍板的事还没定？ |
| 术语、依据 | 名词各指什么；关键结论依据哪些代码位置？ |

「设计」下的子节按项目实际选，没有对应机制的不写。ADR 用五节：标题（名词短语）、状态（提议中、已接受、已废弃）、背景、决定、后果。后果写决定生效后的处境，好坏都写，整篇一到两页。

## 语言要点
- 先结论后细节。评审者通常只读概述和每节首句，结论放后面就会被漏掉。
- 取舍写成「换来什么、放弃什么」，只写本设计自己选择带来的代价，并给出数据或代码依据，后来的读者才能判断前提变了没有。
- 用祈使句写约束和步骤，例如「写入前校验期望版本」。代码不拟人，写「调度器校验参数」，不写「调度器希望参数合法」。
- 论证和因果用短段；顺序动作用编号步骤，并列事项用列表，排版见 `references/formatting.md`。
- 状态、字段、错误名照代码原样写在反引号里，首次出现时给中文名。

## 这一类的反模式
- 写成实现手册：只讲怎么建、不讲取舍，或粘贴完整接口定义、Schema 和大段代码，篇幅涨了，内容也很快过时。
- 只写成功路径，不说失败、超时和竞争时发生什么。
- 把平台差异或实现分支凑成「备选方案」。
