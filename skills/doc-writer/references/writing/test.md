# 测试文档（测试计划、用例、测试报告）
用 ISTQB 测试设计的规范语言讲清测什么、怎么测、测到什么程度可以放行。
读者是测试、研发和发布决策者。

## 标准章节
| 测试计划章节 | 要回答的问题 |
|---|---|
| 范围与目标 | 测哪些功能和质量特性，不测哪些，依据哪份需求或设计？ |
| 测试方法 | 分哪些层级和类型，各用什么测试设计技术？ |
| 准入与退出准则 | 什么条件下开始测，满足什么条件算测完？ |
| 环境与数据 | 需要什么环境、配置和测试数据？ |
| 风险（按 `SKILL.md`） | 哪些产品风险决定了测试的优先顺序？ |
| 进度与分工（可选） | 谁在什么时候完成哪部分？ |

| 测试报告章节 | 要回答的问题 |
|---|---|
| 结论 | 对照退出准则，能否放行，有什么前提？ |
| 执行概况 | 计划多少、执行多少、通过多少、失败多少、跳过多少？ |
| 覆盖 | 覆盖项是什么，分母是多少，覆盖了多少？ |
| 未修复缺陷与残余风险 | 还有哪些缺陷没修，带着它们放行的风险是什么？ |
| 偏离计划（可选） | 哪些地方没按计划做，为什么？ |

测试用例每条写前置条件、输入、操作、预期结果、后置条件。

## 语言要点
- 用标准技术名：等价类划分、边界值分析、判定表测试、状态迁移测试。名字一致，读者才知道覆盖准则是什么。
- 覆盖率写明覆盖项和分母，例如「有效迁移 12 条，测了 10 条」。只给百分比时，读者不知道漏了什么。
- 结论只来自真实运行记录，写明提交、环境和日志位置。用例存在不等于已通过。
- 跳过、错误、未执行与通过、失败分开计数，不算进通过率的分子。

缺陷：
- 不写「无缺陷」。测试只能发现缺陷，证明不了没有缺陷。
- 缺陷报告分开写预期结果和实际结果，附复现步骤和日志。严重程度和优先级是两个字段，分开填。

## 这一类的反模式
- 把覆盖率阈值当目标，达标之后就没人再补测。
- 用重跑掩盖不稳定的测试，只报最后一次的结果。
