# 技术类文档

技术设计、API 文档、ADR、测试报告、Runbook、Reference 和 Explanation 读本文件。技术类文档回答"它怎么工作、为什么这样设计、出错时怎样"，读者是开发者、评审者和运维。

## 1. 语言

用技术设计的规范语言：术语准确，讲机制、约束和取舍。

- 用领域通用术语（至少一次、幂等、围栏令牌、乐观并发、单写者），第一次出现时用一句话说明在本项目中的含义。
- 函数、字段、状态、错误、配置项照代码写。关键标识第一次出现时附 `文件:行号` 或相对链接，不在每段末尾堆"依据"；链接路径相对文档所在位置，写完核对能打开。
- 讲"为什么"：每个关键设计写它解决什么问题、放弃了什么。

## 2. 技术重点

先研究项目实际有哪些重点，再决定写哪些；下表是清单，不是必填项。每项写到读者能理解机制、能据此改代码或排查问题。

| 重点 | 写什么 | 推荐呈现 |
|---|---|---|
| 问题与约束 | 要解决的问题，影响设计的约束（性能、一致性、兼容、团队、部署环境） | 短段 |
| 组成与职责 | 组件、各自职责与依赖方向，进程或存储边界 | 组件图 + 职责表 |
| 数据模型 | 实体、字段、类型、约束、索引、生命周期；字段之间的不变量 | 字段表，必要时 ER 图 |
| 状态机 | 全部状态、转换、触发者、守卫条件、终态；非法转换的结果 | 状态图 + 转换表 |
| 主要流程 | 关键操作的步骤，包括失败、超时、并发竞争路径 | 时序图（多方参与时）或编号步骤 |
| 错误处理 | 错误分类、调用方看到什么（异常、返回值、状态）、能否重试、幂等保证 | 错误表 |
| 并发与一致性 | 锁、事务边界、隔离级别、竞争场景下的结果 | 短段 + 时序图 |
| 兼容与迁移 | 版本演进、迁移步骤、回滚、旧数据的处理 | 编号步骤或表 |
| 容量与性能 | 有数据才写：指标、测量方式、限制 | 表 |
| 安全 | 有真实边界才写：信任边界、权限、敏感数据 | 短段 |
| 示例 | 能运行的最小示例，覆盖主流程和一个失败路径；运行过再写结果 | 代码块 + 输出 |
| 取舍与备选 | 现实候选、各自代价、为什么选当前方案 | 比较表 |

核心机制涉及多方交互时（如领取、超时回收、迟到的确认被拒、队列满时写入被拒），用时序图画出完整场景，失败和竞争分支用 `alt` 画在图里，不只画成功路径。

## 3. 架构决策的论证

提出或评审架构决策时，下列常见方案要附带适用条件和代价：

| 方案 | 必须说明 |
|---|---|
| 加缓存 | 失效策略、一致性代价、冷启动 |
| 加重试 | 幂等保证、重试风暴防护、超时上限 |
| 加消息队列 | 顺序要求、消费失败处理、积压监控 |
| 加服务或中间层 | 新增的运维成本、谁来维护 |
| 加人工审核 | 审核延迟的影响、审核标准能否量化 |

识别这些反模式并改掉：

| 反模式 | 信号 |
|---|---|
| 万能组件 | 一个组件同时负责编排、决策、存储、权限 |
| 伪复杂度 | 组件变多但职责没变多；箭头很多却说不清数据方向 |
| 只有正常路径 | 不说失败时发生什么 |
| 安全关键词堆砌 | 只出现"加密、鉴权、审计"，没有具体边界和机制 |
| 抽象命名 | "智能决策中心""统一能力平台"说不清具体职责 |
| 套模板 | 不看团队、系统和业务约束，直接搬标准架构 |

检验：一个方案如果不了解具体场景也能提出，多半是套话而不是设计。

## 4. 测试与验证

测试报告和设计中的验证部分按以下口径写：

- 写明计数单位：用例、执行项（用例 × 配置）还是尝试（同一执行项的多次运行）。首次通过和重试后通过分开说。
- 跳过、错误、未执行与通过、失败分开记录，不计入通过率分子；每个指标写清分母。
- 结论来自对应的运行记录，引用提交、环境和日志位置；源码或用例存在不等于已通过。
- 关键失败单独列出，不被高通过率淹没。
- 设计阶段的验证写成用例：输入、前置状态、操作、预期、判定依据；计划、用例、实现、实际运行分开写，没运行的不写结果。
- 人工或模型评审作判定器时，说明判据和已知误判。

## 5. 代码与示例

- 示例从真实代码出发，能运行的先运行再写输出；构造示例标明用途。
- 伪代码和可执行代码分开标明，保留错误处理和清理语义。
- 新代码或代码级设计按[本次代码规范](../assets/templates/tech-design/code-conventions.md)。
