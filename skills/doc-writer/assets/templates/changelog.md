# Changelog
> 面向用户的版本变更记录：每个版本做了什么、破坏了什么、用户需要怎么升级。提交消息面向工程师，Changelog 面向用户——两种读者，不可混用。

> **示例使用范围**：保留已核验的 Requests Security 条目，属于非官方中文翻译与格式改编，只示范历史更新说明，不是目标项目事实或当前升级建议。见[来源说明](../examples/SOURCES.md)。

## 变体选择

```
读者是谁、发布节奏如何？
  ├─ 开源项目 / 库，按版本发布            → Keep a Changelog（默认）
  ├─ 产品发布，面向终端用户               → Release Note
  └─ 仅内部消费，无外部用户               → Keep a Changelog（精简）
```

## 变体 A: Keep a Changelog（默认）

遵循 keepachangelog.com 规范。面向开发者用户，按语义化版本组织。

### 必需内容

| 必需内容 | 本节回答 | 排版 |
|--------|------|------|
| `## [Unreleased]` 与 `## [x.y.z] - YYYY-MM-DD` | 尚未发布的变更放哪？这个版本号是什么、什么时候发布的？ | 最新版在前，`[Unreleased]` 在最上 |
| 变更分类 | 加了什么、改了什么、弃用了什么、删了什么、修了什么、修了什么安全问题？ | 版本标题下只用 6 个分类，只列有条目的类：新增（Added）、变更（Changed）、弃用（Deprecated）、移除（Removed）、修复（Fixed）、安全（Security）；分类名照 Keep a Changelog 1.1.0 写英文原名（`### Added` 等），发布工具按它解析；条目正文按项目语言写 |

### 按需模块

| 模块名 | 本节回答 | 排版 | 格式规范 | 保留条件 |
|--------|------|------|---------|-----------|
| 升级说明 | 用户具体怎么从上个版本升级？ | 有序步骤 | 步骤化的升级操作 + 代码 Before/After | 有具体代码变更才有效；"请参考文档"无效 |

破坏性变更不单设节：在所属分类内用条目前缀 `**破坏性变更：**`（Common Changelog 的 `**Breaking:**`）标出，并按差异对照（Before/After）写明用户必须改什么；本包扩展，Keep a Changelog 无此约定。安全条目写 CVE 编号（如有）+ 影响范围 + 修复方式 + 是否需要用户行动，"修复了安全问题"无效；弃用条目写被废弃的 API/功能 + 替代方案 + 计划移除版本（未定时写"移除时间未定"），移除时间未知不是删掉弃用信息的理由。

### 变更条目写法规则

每条变更遵循以下规则（祈使语气和附引用来自 Common Changelog，其余为本包要求）：

- **祈使语气**：用"Add"、"Fix"、"Remove"开头，不用过去式
- **一条一事**：按理解需要换行，保留必要条件与行动顺序
- **说影响不说实现**：用户关心"搜索现在支持模糊匹配"，不关心"重构了 SearchService 类"
- **破坏性变更置顶**：每个分类内破坏性变更排在最前，加 `**破坏性变更：**` 前缀
- **附引用**：条目末尾附 PR/issue 链接，如 `(#123)`
- **不直接转换提交记录**：提交消息写给开发者，更新说明写给使用者；可以从提交记录生成草稿，但要按使用者影响重写（参见 Sophia Willows 的文章）

### 示例（已核验：Requests 2.31.0 Security 条目）

> **非官方中文翻译与格式改编，2026-09-06**：摘自 Requests 的 [HISTORY.md 第 9–33 行](https://github.com/psf/requests/blob/147c8511ddbfa5e8f71bbf5c18ede0c4ceb3bba4/HISTORY.md#L9-L33)。只调整版本/分类标题、换行及示例 URL 的行内代码标记，不新增事实或迁移建议。Requests；Copyright 2019 Kenneth Reitz；[Apache-2.0 全文](../examples/licenses/requests-LICENSE.txt)与[原 NOTICE](../examples/licenses/requests-NOTICE.txt)随包保留。见[核验记录](../examples/SOURCES.md#requests-2310)。

只模仿 Security 条目如何交代影响范围、触发条件、不受影响的情况及用户行动。这是 **2023 年的历史更新说明，不是当前升级版本建议**，也不代表 Requests 原文遵循 Keep a Changelog。“一条一事”不能成为删掉安全条件或行动顺序的理由；未出现的分类不补造。

````markdown
## [2.31.0] - 2023-05-22

### Security

- Requests v2.3.0 至 v2.30.0 存在漏洞：跟随 HTTPS 重定向时，
  可能将 `Proxy-Authorization` 请求头转发给目标服务器。

  当代理配置中包含用户信息（`https://user:pass@proxy:8080`）时，
  Requests 会构造 `Proxy-Authorization` 请求头，
  并将其附加到请求中，用于向代理进行身份验证。

  此前，Requests 收到重定向响应后，会错误地重新附加
  `Proxy-Authorization` 请求头，导致其值经由隧道连接发送给目标服务器。
  强烈建议在 URL 中设置代理凭据的用户升级到 Requests 2.31.0 或更高版本，
  以防止意外泄露，并在此次变更完全部署后轮换代理凭据。

  不使用代理，或不通过代理 URL 的用户信息部分提供代理凭据的用户，
  不受此漏洞影响。

  完整详情见 [GitHub 安全公告](https://github.com/psf/requests/security/advisories/GHSA-j8r2-6x86-q33q)
  和 [CVE-2023-32681](https://nvd.nist.gov/vuln/detail/CVE-2023-32681)。
````

## 变体 B: Release Note

面向终端用户（非开发者）的产品发布说明。关注用户价值而非技术细节。

### 必需内容

Release Note 的章节与顺序固定为：概述 / 亮点 / 升级说明 / 变更列表 / 已知问题 / 致谢（后两项按需）。

| 必需内容 | 本节回答 | 排版 |
|--------|------|------|
| 概述 | 这次更新叫什么、什么时候发布？最重要的变化是什么？ | 倒金字塔（最重要的变化一句话说完），版本号与日期写在首句 |
| 亮点 | 这次更新最重要的 1-3 个变化是什么？ | 倒金字塔 |
| 升级说明 | 用户需要做什么才能用上新版？ | 有序步骤 |
| 变更列表 | 还有哪些改进和修复？ | 分类列表 |

### 按需模块

| 模块名 | 本节回答 | 排版 | 格式规范 | 保留条件 |
|--------|------|------|---------|-----------|
| 已知问题 | 这个版本有什么已知但未修复的问题？ | 列表 | 问题描述 + 影响范围 + 临时规避方法 | 有规避方法才有效；"已知存在问题"无效 |
| 致谢 | 谁为这个版本做了贡献？ | 列表 | 贡献者名 + 贡献内容（非必须） | 社区项目有效；纯内部项目可删除 |

## 类型验证标准

| 检查项 | 判定标准 |
|--------|---------|
| 破坏性变更醒目 | 破坏性变更在视觉上第一眼可见（置顶 + `**破坏性变更：**` 前缀），不埋在列表中间 |
| 每条有具体影响 | 每条变更说明了对用户的具体影响，无"各种改进"、"性能优化"等模糊汇总 |
| 面向正确读者 | 条目用用户能理解的语言写，不是提交消息的复制粘贴 |
| 日期格式统一 | 使用 ISO 8601（YYYY-MM-DD），无地区歧义格式 |
| 版本号可追溯 | 版本号与 git tag 一致 |
| 升级可执行 | 破坏性变更有具体的代码升级指引（Before/After 或步骤），不只说"已变更" |
| 无自动生成痕迹 | 无 `feat:`、`fix:` 前缀，无 merge commit 噪音，无未经编辑的提交消息 |
