# 完整检查入口

主模型对最终交付全文和选定的版本/时间点做一次完整检查，脚本只补充字面候选。确认不了的项目记为"待确认"或"未检查"。

## 必读来源

- [共同约束](../docs/modules/constraints-common.md)与[编写规则](../docs/modules/constraints-writing.md)的完整 C/G 规则、条件和豁免；适用时加[D1（架构文档质量清单）](../docs/modules/constraints-architecture.md)。
- 当前[类型模板](../templates/_index.md)的类型验证标准。
- [验证管线](../docs/modules/5.3-verification-pipeline.md)：做内容对齐读 5.3.1，去重读 5.3.2，类型专用验证读 5.3.5，长文读 5.3.4。

已完整读到且仍可用的规则不必重读；缺失或版本变化时补读。

## 1. 模型主检

下表把 11 项收尾检查归入五类语义验证（V1–V5），一次过完。表格是检查顺序，规则以原约束为准。

| 收尾项 | 规则 | 检查什么 |
|---|---|---|
| #1 禁用清单 | G1（禁用模式清单）、G4（中文表达与排版） | 按上下文裁决全部模式，含脚本识别不了的占位符、跨句和转折否定句式；核对 G4 的句子、结构与排版规则；判断引用、定义、度量和必要性论证的豁免 |
| #2 标题、#3 首尾 | V1、C1c（结论先行）、C1e（金字塔结构） | 标题准确预期内容，论证类章节标题写成结论句；章节和论证段落先给要点；首段含核心结论，末段落在决策或下一步行动，首尾没有铺垫和重复总结；只读各级标题和每节首句能复述全文结论 |
| #4 数字、#5 认知状态 | V2、G2（真实性护栏） | 数据和估算有来源或依据，缺口写出验证方式；事实、假设、判断可分辨；没测的写没测，限制写具体条件；目标值、契约值说明性质 |
| #6 判断 | V3、C3（判断义务）、G3（排除性检验） | 文档职责要求判断时，有立场、理由、排序和取舍，并通过排除性检验；参考文档陈述契约，纪要记录实际决议 |
| #7 可操作性 | V4、C4（可操作性） | 概念、原则、组件能回答"具体做什么"；Quickstart 首屏用必要输入完成主要任务并确认结果，辅助依赖不阻断本可用的主要功能；作者自查、选型说明移出读者的操作路径 |
| #8 范围 | V5、C5（范围锁定） | 先对照用户请求检查选题、交付物和关键内容有无遗漏，再查正文是否越界；需求验收要点逐项对应原始需求中的适用关键要求，每项都有可判断的验收条件，不以实施状态、交付物齐全或泛化质量项代替；项目正文写项目本身，本轮变更记录归对应文档 |
| #9 对称性、#11 结构化表达 | C1a（反对称）、5.2、5.8 | 必需内容、必需字段和固定格式保留，其余按任务组织；结构反映真实的并列、分类、顺序或对应关系；动作步骤以祈使动词开头；架构图回答本节职责、边界与依赖，能渲染时渲染核对，无渲染工具时核对语法并注明未渲染 |
| #10 术语 | V1、C6（一物一名） | 用常用语言说明对象、行为、条件与结果；名称与含义一致，标准名和代码标识照用 |

再按当前类型、变体和分支执行模板中的类型验证，核对需求、契约、代码约束与验证是否对应。详细设计检查重点注释的交接，有代码时核对实际注释。跳过某项须有模板条件作依据。涉及测试判定时，按[测试证据指导](../docs/modules/test-evidence-presentation.md)的触发条件核查，包括人工或模型评审和自定义判定器。

## 2. 候选扫描与裁决

按入口给出的命令运行 `runtime/doc-lint.py`，对象是待交付文件。

- 按 G1 裁决每个候选：无必要的措辞删除，其余修正、保留或标记待确认。
- `<!-- doc-lint: ignore-next-line 原因 -->` 只豁免下一物理行的脚本候选，模型检查照常进行。只在候选经裁决确需保留时手动添加，不为消除候选自动或批量添加。
- 脚本排除的代码和 URL 仍要核对与文档描述是否相符。
- 退出 `0` 表示扫描完成，可带警告；退出 `2` 表示执行故障。脚本不可用时说明原因，由模型完成检查。
- 工具要求批准、拒绝操作或安全检查无法分析命令时，停止该操作，等待新的明确授权。

## 3. 内容对齐与去重

**内容对齐**（文档引用了代码、接口、配置或运行记录时执行）：按 5.3.1 确定证据版本后核对。实现描述对齐所选实现，目标设计标注差异，历史记录保持历史原貌。测试结论来自对应运行记录。

**去重**（所有文档）：按 5.3.2 确定阅读单元后检查重复。摘要的必要重叠，以及独立端点、语言轨道、操作条目各自需要的前置条件和安全信息保留，让每个阅读单元自足。

## 4. 关键文档读者测试

按[5.9 读者测试](../docs/modules/5.9-reader-testing.md)的触发条件执行：需多人评审的架构决策或技术方案用 fresh reader；参考资料可选；内部笔记、草稿和快速路径不做。

主模型按读者任务出题，把实际交付的文档、角色和问题交给 reader，不附需求背景、写作讨论或预期答案。reader 检查操作、查询或判断能否完成，原始需求对照仍由主模型做。同一段落修正三次仍未解决时，标记需人工审阅。无法启动 reader 时写"独立读者测试未执行"。

## 5. 修正与交付

发现问题就修正对应段落，从该步重新检查，并重验修改波及的项：改术语核对全文命名，改数字核对关联表格和结论，补写段落复查范围和来源。最终文件再做一次候选扫描与语义确认，未解决的问题列为缺口。

交付说明写版本、路径、核对范围、差异、结果和未检查原因，用短段落而非勾选表。关键文档另汇总待验证内容与验证方式，本轮检查记录归对应文档。未保存文件时文末一行写明候选脚本未运行。

## 检查顺序

```
Step 1  模型主检 + 类型专用验证 + 候选裁决        必做
Step 2  内容对齐（5.3.1）                         引用代码、配置或运行结果时做，快速路径同样适用
Step 3  去重（5.3.2）                             所有文档
Step 4  读者测试（5.9）                           关键文档；未执行时标注
```
