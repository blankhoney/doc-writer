# 程序详细设计指导

从[技术设计](../tech-design.md)进入，保持原有变体必需内容；以下内容放入方案，代价和未决归原节。新项目可直接依据需求设计，路径和接口未存在时标为拟议。

先读[代码规范](code-conventions.md)，形成当前任务的代码约束。按 PRD、初版方案和选定代码版本核对关键需求，主动补实现缺口；新提议标为"拟议"。

## 展开实现所需内容

| 内容 | 交接到什么程度 |
|---|---|
| 实现落点 | 已有／拟新增模块、文件、职责、改动种类及依赖顺序；文件树注明基线和拟议／实际；依赖与包布局见下 |
| 接口与数据 | 签名、类型、字段、单位、可空性、约束、返回值、副作用和错误；沿用公共契约中的名称 |
| 执行逻辑 | 入口、调用、分支、算法和事务边界；伪代码保留异常、退出与清理，省略范围可辨认 |
| 状态与失败 | 状态、触发、守卫、动作、不变量与可见结果；按需覆盖幂等、并发、超时、取消、重试停止和资源释放 |
| 兼容与实施 | 新旧接口映射、实施依赖、迁移／回退条件；变更架构决定时明确提出待决 |
| 代码规范 | 按代码规范指导交接本次规则；重点注释写明位置、解释内容与核验方式，无代码示例也须交接；小任务用条目 |
| 验证 | 需求／风险对应输入、前置状态、操作、预期、判定依据及测试接入点；按共用测试指导区分计划、用例、实现和实测 |

能用签名、类型或短步骤说清的内容不再画图；复杂交互按 5.8 表达。设计调用链是预期路径，实际调用栈须有运行记录。拟议代码保持选定命名、类型与注释规则，只写与决策相关的部分。

### 依赖表与包布局

交代当前方案的依赖与代码落点，沿用项目现状。

**依赖表**：列实现本方案或理解边界所需的依赖，包括未变但关键的既有依赖；锁文件和全部传递依赖不必转储。

| 字段 | 写法 |
|---|---|
| 依赖项及类别 | 内部／第三方／标准库／外部服务；构建与测试专用另标 |
| 用途 | 一句话；完整选型论证放回原章节 |
| 版本或契约约束 | 写声明的范围；锁定值另行注明；内部包沿用项目版本方式 |
| 使用方 → 提供方 | 箭头表示依赖方向 |
| 变更状态 | 既有沿用／拟新增／升级／替换／移除／候选待决 |
| 依据 | 依赖清单、导入代码、契约或已确认决策；拿不到标"待核实" |

许可、安全与失败处理在影响选型或行为时展开。没有新增第三方依赖时明确写出。

**包布局**：范围是目标模块及直接依赖，先写现状再写目标，语言、构建与命名沿用项目。

- 只展示相关主干或受影响子树，保留包／模块边界、公开入口、关键实现与测试落点。
- 每项标既有／新增／修改／移动／删除或拟定；移动写"旧路径 → 新路径"。
- 说明对外入口、内部实现与允许的依赖方向。
- 树、依赖表、接口与测试用同一套名称；树上写清的职责不再列表重复。包树回答"放在哪里"，结构关系另用结构图。

局部小改动、纯架构设计或轻量文类，依赖与布局不变时，用一段说明加相关路径即可；影响理解的既有关系照写。

## 分支检查

- 契约：输入输出、约束、副作用与错误能供调用方使用；字段与上层约定一致。
- 行为：正常、边界与适用失败路径连贯；状态及不变量、事务／异步边界、取消与清理可定位。
- 落点：关键需求对应模块与文件；未知内容标为拟定，实施顺序无缺失依赖。
- 依赖与布局：依赖类别、契约状态与使用方向清楚，布局标记与公开入口一致；轻量任务只写必要的依赖与路径。
- 代码约束：有取样依据或新项目草案；风格、命名、类型一致，重点注释已交接且可核验；公共兼容和范围外代码保持原状。
- 验证：成功条件可观察，判定有依据；缺证据的项记为未验证，关键风险与验证缺口列全。
- 复杂度与未决：落实父模板 D1 和观测要求，每个组件都有需求支撑；关键待决及其影响清楚。
