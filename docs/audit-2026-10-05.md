## 2. Eval 首轮结果与失效原因

用例在 `evals/`，对应 `tests/SMOKE.md` 的三个场景，每个用例带无 skill 基线。实际每个用例运行 1 次，评审模型 haiku 投 3 票。总成本 $2.34，耗时 357 秒。

| 用例 | 带 skill | 无 skill | 带 skill 轮数 / 成本 | 无 skill 轮数 / 成本 |
|---|---|---|---|---|
| ci-report-no-log | FAIL（1/3 票） | PASS（3/3） | 19 / $0.75 | 3 / $0.08 |
| cli-reference | FAIL（1/3 票） | FAIL（0/3） | 16 / $0.73 | 6 / $0.08 |
| tech-design-memo | FAIL（0/3 票） | FAIL（0/3） | 14 / $0.62 | 5 / $0.07 |

**结果不能当作 skill 不达标的证据。** 评审器只看最后一条回复（`focus: last_message`），而成功标准里有"实际读取了必读文件""没有写文件或运行 shell"等只能从 trace 判断的项，评审器只能判 FAIL。人工查看三份带 skill 的输出：四节结构齐全，有"未保存文件，未运行候选脚本"注记，没有编造通过数，内容与源码对得上。

eval 仍然给出了两个可信信号：

- **成本**：带 skill 的运行轮数约是无 skill 的 3–6 倍，成本约 9 倍，与 B1 一致。
- **工具受限**：tech-design 运行中 Glob 被拒；ci-report 运行因此无法确认 `tests/` 下有哪些文件，只能写成缺口。

**下一轮怎么改**：

1. 内容标准留给 llm 评审器，只写最后一条回复能看出来的项。
2. 读取行为改用 `tool_used` 评审器，例如要求 `Read` 读过 `constraints-common.md`。
3. 写文件和 shell 已被 `allowed_tools` 排除，不再列入标准。
4. 每个用例跑 3 次，以压低单次波动。

## 3. 文风与格式建议

先说结论：skill **要求**文档结论先行，`SKILL.md` 自身却是按流程罗列条款，读者要读完才能拼出主线。金字塔原理在包里只用到了两处：C1c"结论先行"和 5.2.2 的"倒金字塔"排版。纵向问答、横向分组、SCQA 序言都没有用上。

### 3.1 SKILL.md 自身的文风

实测数据：80 句，中位长 34 字，最长 162 字，16 句超过 60 字；"不"字每百字 1.7 次，约是 `prepare.md` 的 2 倍。

- **先给主线，再给细则**：开头用 3–5 行说清"读什么 → 写什么 → 怎么验 → 交付什么"，现在的条款下沉到对应阶段。
- **否定句改为肯定句**：例如"不能凭文件名、摘要代替原文"改为"用 Read 读原文"。禁止项集中放进一张"不做"表，不散在各段。
- **拆长句**：超过 60 字的句子按条件拆开，一句只管一个条件。最长的是资源表单元格和 §4 的授权段落。
- **资源表只写时机**：表格单元格里的规则解释移到正文，表格只留"文件 | 何时读"。
- **去重**：同一条规则（"不凭摘要""0 命中≠通过""不编造"）只在一处陈述，其他地方引用。

### 3.2 把金字塔原理补进写作规则

建议放在 `constraints-common.md` 的 C1 中，作为 C1c 的扩展；检查项放进 `5.9-reader-testing.md`。

| 原则 | 现状 | 建议规则 | 适用类型 |
|---|---|---|---|
| 纵向问答 | 缺 | 每一层回答上一层引出的问题；某节回答不了它上一层引出的问题，就删除或移走 | 全部 |
| 横向分组（MECE） | 缺；C1a 只管反对称 | 同级要点不重叠、不遗漏，同属一类；分组之间无法区分就合并 | 技术设计、PRD、ADR |
| 逻辑顺序 | 缺 | 同级要点必须说明按什么排：时间、结构或重要度；演绎链不超过 4 步 | 全部 |
| 标题即结论 | 缺 | 论证类章节的标题写结论句，不写话题词（"选用单体架构"，而不是"架构选型"） | 技术设计、ADR、测试报告 |
| SCQA 序言 | 缺 | 决策类文档开头用"情境 → 冲突 → 问题 → 答案"，四句以内 | 技术设计、ADR、PRD |
| 结论先行 | 已有（C1c） | 保留 | 全部 |

验证时加一项读者测试：只读各级标题和每节首句，能不能复述全文结论和主要论据。复述不出来，就说明结构没有立住。

### 3.3 格式

- 编号只留一套：现在 §5.x、C/G/D/H/V 编号与"原 11 项"混用，运行时文件只保留 C/G/D 一套。
- 模板中的"排版"字段直接链接到 5.2.2，不再重复描述。
- 审计和整改文档本身按本节规则写：先结论，再证据。

## 5. 防御性说明清理

## 6. 是否融合 humanizer-zh 或 caveman

- **humanizer-zh（op7418/Humanizer-zh，MIT）**：挑选借用，不整包融合。它的 31 种模式中约 6 种已在 G1 中；G1 缺失且适用于技术文档的有破折号滥用、限定词堆叠、粗体当装饰、首句复读标题、客服腔、"的"字堆叠、被字句堆叠、借权威。建议按 G1 表格格式补入，连同"保留"例子；字面模式补入后扫描器可直接使用。整包约 20KB，面向博客与长文，会抵消本轮压缩的上下文。
- **caveman**：不适合。它为聊天回复压缩语法词、写碎句，与 C1d、C6 冲突；用于压缩规则文件也会增加歧义，影响规则遵守。

## 9. Codex 日志被删的根因

第一轮全仓审查的 Codex 日志在运行中被删，最终汇总丢失。监视 scratchpad 并回查进程记录后确认：并行运行的 Opus 子 agent 在清理自己的临时文件时执行了 `rm -rf <scratchpad>/*`，而子 agent 与主会话共用同一个 scratchpad。eval 正常结束时不会删除文件（eval3 全程监视无删除事件）。

防止再犯（写入 `~/.claude/AGENTS.md`）：

- Codex 复审改用 `~/.local/bin/codex-review`：日志与最终回答写到 `/tmp/codex-review/`，最终回答用 `-o` 单独落盘，缺失时非零退出。第二次复审按此运行，`.final.md` 完整保留。
- scratchpad 清理只删自己建的文件；派子 agent 时要求它在 `<scratchpad>/<agent名>/` 下工作并只删该子目录。
- 结束进程按 PID kill，不用 `pkill -f`（会匹配到执行它的 shell 自身）。
